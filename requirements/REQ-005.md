# REQ-005 — Git destructivo prohibido a los agentes: el trabajo de un subagente no es atómico para git
Estado: en-revisión
Módulo: hooks (guard-git.sh nuevo, guard.sh, lib.sh) + templates/ + skills/arnes-upgrade + banco tests/escenarios/hooks/run.sh
Prioridad: alta
Versión destino: 1.31.0
Sensible a seguridad: sí
QA: con-hallazgos (2026-09-06, vuelta 2; QA-101 cerrado, falta el write-back del fin de opciones y de -S/-W; ver docs/qa/1.31.0.md)
Seguridad: pendiente
Hallazgos abiertos: QA-110 (contrato)
Rigor: critico

## Historia
Como dueño del trabajo que un agente todavía no ha comiteado, quiero que ningún agente —ni siquiera
la sesión coordinadora— pueda ejecutar por `Bash` **ninguno de los subcomandos de git declarados
destructivos en `git.prohibidos`, en cualquiera de sus ortografías** —flag corto o su forma larga
equivalente, agrupado o suelto, con el alias histórico del subcomando—, para que un `git clean` o un
`reset --hard` emitido «para dejar limpio» no borre horas de trabajo que git no puede devolver.

**La promesa es la que la máquina puede sostener, y se escribe así a propósito (precisión del
2026-09-06).** El alcance de esta puerta es **la lista declarada** —que es **mapeo** del proyecto y
se amplía (CA-19, CA-34)—, no «todo comando de git capaz de destruir algo»: `git worktree remove
--force` destruye un árbol de trabajo y hoy **no** está en la lista por defecto, así que pasa, y eso
es una decisión del mapeo, no un fallo de la puerta. Fuera quedan también, y así está declarado, git
ejecutado desde un script o un intérprete. Lo que **no** admite excepción —y es lo que este REQ sí
promete— es que una entrada **ya declarada** se escape por cómo se escribe: `git clean --force`
borra exactamente lo mismo que `git clean -f`, y `git stash save` es el alias todavía funcional de
`git stash push`.

## Criterios de aceptación

### Bloque A — lo que deniega

- **CA-01** — Dado un proyecto del arnés y la sesión coordinadora, Cuando emite por `Bash` el comando `git clean -fd`, Entonces el hook responde DENY y el motivo nombra el subcomando prohibido y dice por qué (el trabajo sin comitear no es recuperable) y cómo seguir (comitear, o pedirlo al humano).
- **CA-02** — Dado el **mismo** comando emitido por el agente `desarrollador`, Cuando llega la llamada, Entonces el hook responde DENY **igual**: esta puerta es del **comando**, no de la identidad — es justo lo que la distingue de `guard-codigo`, y por eso también alcanza a la coordinadora.
- **CA-03** — Dado cualquier agente, Cuando emite `git reset --hard` o `git reset --hard HEAD~1`, Entonces el hook responde DENY en los dos casos.
- **CA-04** — Dado cualquier agente, Cuando emite `git checkout .` o `git restore .`, Entonces el hook responde DENY en los dos casos.
- **CA-05** — Dado cualquier agente, Cuando emite `git stash` o `git stash push -u`, Entonces el hook responde DENY en los dos casos.
- **CA-06** — Dado cualquier agente, Cuando emite `cd sub && git clean -fd`, `git -C proj reset --hard`, `(git reset --hard)`, `x=$(git stash)` o `git clean -fd | tee log`, Entonces el hook responde DENY en los **cinco**: el subcomando se reconoce esté donde esté dentro del comando.
- **CA-07** — Dado un heredoc **sin citar** cuyo cuerpo contiene la expansión `$(git clean -fd)`, Cuando llega la llamada, Entonces el hook responde DENY: con el delimitador sin citar bash ejecuta de verdad esa sustitución, y aquí se aplica el **mismo descuento** de heredocs y comillas que usa el detector de escrituras.

### Bloque B — lo que NO deniega (controles positivos)

- **CA-08** — [control] Dado cualquier agente, Cuando emite `git stash list` o `git stash show`, Entonces el hook responde ALLOW: son lecturas, no destruyen nada.
- **CA-09** — [control] Dado cualquier agente, Cuando emite `git restore --staged archivo.ts`, Entonces el hook responde ALLOW: saca del índice, no toca el árbol de trabajo.
- **CA-10** — [control] Dado cualquier agente, Cuando emite `git clean -n` o `git clean --dry-run`, Entonces el hook responde ALLOW: enumeran lo que borrarían y no borran nada.
- **CA-11** — [control] Dado cualquier agente, Cuando emite `git reset --soft HEAD~1` o `git reset archivo.ts`, Entonces el hook responde ALLOW: sin `--hard` no se pierde el árbol de trabajo.
- **CA-12** — [control] Dado cualquier agente, Cuando emite `git checkout rama`, `git checkout -b rama` o `git restore --source=HEAD~1 archivo.ts`, Entonces el hook responde ALLOW: sólo la forma con `.` arrasa el árbol entero.
- **CA-13** — [control, el texto no es el comando] Dado cualquier agente, Cuando emite `git commit -m "no uses git clean"`, `git commit -m 'reset --hard revertido'` o un heredoc **citado** (`<<'EOF'`) cuyo cuerpo dice `git clean -fd`, Entonces el hook responde ALLOW en los tres: lo entrecomillado y el cuerpo literal de un heredoc se descuentan antes de mirar el comando.
- **CA-14** — [control] Dado cualquier agente, Cuando emite `github clone x`, `gitk`, `mygit clean` o `legit clean`, Entonces el hook responde ALLOW: `git` se reconoce como **token** de comando, no como subcadena.
- **CA-15** — [control] Dado cualquier agente, Cuando emite `echo "git clean"` o `grep -r "git stash" .`, Entonces el hook responde ALLOW.
- **CA-16** — [control, no regresión] Dado el conjunto de comandos de las secciones existentes del banco que hoy responden ALLOW y contienen `git` (por ejemplo `git status`, `git log`, `git diff`, `git add`, `git commit`), Cuando corren contra la candidata, Entonces todos siguen en ALLOW.

### Bloque C — el manifiesto: mecanismo aquí, mapeo allí

- **CA-17** — Dado un manifiesto **sin** el bloque `git`, Cuando llega `git clean -fd`, Entonces el hook responde DENY: `git.activo` vale `true` por defecto y ésta es **la única novedad de 1.31.0 encendida por defecto**.
- **CA-18** — [control] Dado `git.activo: false`, Cuando llegan los comandos de CA-01 a CA-06, Entonces el hook responde ALLOW en todos: el proyecto puede apagar la puerta con un acto explícito.
- **CA-19** — Dado `git.prohibidos: ["push --force"]` (lista propia que **sustituye** a la de por defecto), Cuando llega `git clean -fd`, Entonces el hook responde ALLOW; y Cuando llega `git push --force origin main`, Entonces responde DENY: la lista es del proyecto, la comparación es del arnés.
- **CA-20** — Dado `git.prohibidos: []`, Cuando llegan los comandos de CA-01 a CA-06, Entonces el hook responde ALLOW en todos: una lista vacía es una decisión declarada, no un error.
- **CA-21** — [la regla de casado] Dado un `git.prohibidos` cuyas entradas tienen la forma `subcomando [token...]`, Cuando llega un comando de git, Entonces la entrada casa **si y sólo si** el subcomando coincide y **todos** los tokens de la entrada están presentes en ese segmento, **en cualquier orden**; con **tres** precisiones que la regla declara y el banco mide:
  1. **Flags cortos, por letra.** Un token que es un flag corto casa cuando **todas sus letras** aparecen en un **mismo grupo** de flags cortos del comando: `-f` casa con `-f`, `-fd`, `-fdx` y `-ffd`, y **no** casa con `-n` ni con `-d`. Así, Dado `clean -f`, Cuando llega `git clean -fd`, Entonces **DENY**, y Cuando llega `git clean -n` o `git clean --dry-run`, Entonces **ALLOW** (CA-10 se conserva intacto).
  2. **Ortografías equivalentes de un token declarado (write-back de QA-101, 2026-09-06).** Un token de la entrada casa **también** cuando el comando lo escribe en **otra ortografía de la misma opción o del mismo subcomando**, según una tabla del **arnés** (mecanismo, no mapeo) que hoy declara al menos: `-f` ≡ `--force`, `-d` ≡ `--directory` (en `clean`), `-x`, `-n` ≡ `--dry-run`, `-u` ≡ `--include-untracked`, `--all` ≡ `-a` (en `stash`), y el **alias histórico** `stash save` ≡ `stash push`. Así, Dado `clean -f`, Cuando llegan `git clean --force`, `git clean --force -d` o `git clean -d --force`, Entonces **DENY** en los tres —medido el 2026-09-06: hoy los tres salen **ALLOW**, porque el casado compara flags cortos por letra y **salta todo argumento que empiece por `--`**—; y Dado `stash push`, Cuando llega `git stash save "wip"`, Entonces **DENY**. **Controles que no pueden moverse:** Dado `clean -f`, Cuando llegan `git clean -n` o `git clean --dry-run`, Entonces **ALLOW** (CA-10 intacto: la equivalencia mapea cada token a **sus** ortografías, y `--dry-run` es la de `-n`, no la de `-f`); y Dado `stash`, Cuando llegan `git stash list` o `git stash show`, Entonces **ALLOW** (CA-08 intacto: `list` y `show` no son alias de `push`). **Lo que queda fuera de la tabla no casa, y eso es declarado, no accidental:** la tabla es del mecanismo y se amplía con un caso del banco por cada entrada nueva; una ortografía que no esté en ella pasa, exactamente como pasa un subcomando que no está en la lista.
  3. **Una entrada sin tokens casa sólo con el subcomando desnudo.** Dado `stash`, Cuando llega `git stash` o `git stash -u` —ningún token **posicional** detrás; los flags no cuentan como posicional—, Entonces **DENY**; y Cuando llega `git stash list` o `git stash show`, Entonces **ALLOW** (CA-08 se conserva intacto).

  Y como control del reconocimiento: Dado `reset --hard`, Cuando llegan `git reset --hard` y `git reset HEAD~1 --hard` (el token en otra posición del mismo segmento), Entonces **DENY** en los dos; y Dado `clean -f`, Cuando llega `git clean -fd "src"` con el argumento **entrecomillado**, Entonces **DENY**: el reconocimiento del subcomando y de sus flags **no depende de que los argumentos vengan desnudos**, y el descuento de comillas que `guard-git` comparte con el detector de escrituras no puede borrar el segmento del comando.
- **CA-22** — Dado un entorno sin `jq` o un proyecto sin `.arnes/config.json`, Cuando llega `git clean -fd`, Entonces el hook es **inerte** y no bloquea, igual que el resto: el cambio no introduce ninguna dependencia dura nueva ni convierte una carencia de tooling en un bloqueo.

### Bloque D — integración, orden y coste

- **CA-23** — Dado `hooks/guard.sh`, Cuando se revisa el orden de invocación, Entonces `guard-git` corre **antes** que `guard-codigo` y `guard-completado`.
- **CA-24** — Dado un comando que es a la vez `git clean -fd` y una escritura sobre código protegido, Cuando llega la llamada, Entonces el motivo de la denegación es el de **git** (se verifica el texto): la denegación es final y los otros dos guardianes no llegan a correr.
- **CA-25** — [control] Dado un comando que `guard-git` permite y que `guard-codigo` debe denegar (`echo x > src/generated.ts` desde la coordinadora), Cuando llega la llamada, Entonces el hook responde DENY con el motivo de **código protegido**: interponer el guardián nuevo no apaga a los que ya estaban.
- **CA-26** — Dado un comando de Bash que **no** contiene el token `git` (`ls -la`, `npm test`), Cuando pasa por `guard.sh`, Entonces `guard-git` **no lee el manifiesto ni arranca `jq`**: el número de invocaciones de `jq` es el mismo que en **v1.30.3 publicada** (la línea base de no-regresión de 1.31.0; medido con un `jq` instrumentado en el `PATH` que registra sus llamadas). **Precisión de medición (2026-09-06, write-back de QA-104):** lo exigible aquí es que **`guard-git` no aporte ninguna invocación** —su registro propio queda vacío—; el conteo **agregado** del camino común lo gobierna **CA-59 de REQ-007**, porque la lectura del manifiesto que SEC-005 adelantó en `guard-codigo.sh` añade **+1** proceso por comando (2 contra 1 de v1.30.3) que no es de este REQ. Sin esta precisión, el criterio afirmaría en agregado algo que la medida desmiente.
- **CA-27** — Dado un comando que **sí** contiene `git`, Cuando `guard-git` lo evalúa, Entonces añade como máximo **1** lectura del manifiesto por invocación, la evaluación tarda **menos de 200 ms** y la invocación completa del hook responde en **menos de 5 s**.
- **CA-28** — Dado `hooks/guard-git.sh`, Cuando se ejecuta directamente (no `source`), Entonces hace su propio preludio y decide igual que dentro de `guard.sh` — producción y banco ejecutan **la misma función**, no dos copias que puedan desfasarse.
- **CA-29** — Dado el índice de git del PR, Cuando corre el paso de bits de ejecución del CI, Entonces `hooks/guard-git.sh` figura en modo `100755`, igual que el resto de puntos de entrada.

## Notas / alcance

**Origen — un incidente medido.** En un proyecto real se perdieron **~52 archivos de trabajo sin
comitear** en un incidente. La causa de fondo no es el descuido de nadie: **el trabajo de un
subagente no es atómico para git**. Un agente limpia «su» árbol y arrasa el de otro; un comando que
en manos de una persona es rutinario, dentro de una sesión con varios agentes en marcha es
irreversible y silencioso. La regla que funcionó fue comitear tras cada aterrizaje, y esta puerta es
la mitad que la máquina puede sostener.

**Por qué ésta sí nace encendida, y sólo ésta.** Las demás novedades de 1.31.0 cambian **cómo se
juzga** algo y por eso nacen apagadas: encenderlas por sorpresa rompería proyectos que no las
pidieron. Ésta impide una operación **destructiva e irreversible** cuyo valor legítimo dentro de una
sesión de agentes es casi nulo, y cuyo coste cuando falla no se puede deshacer. Un proyecto que la
necesite la apaga con un acto explícito (CA-18) o cambia la lista (CA-19). El caso legítimo —limpiar
de verdad el árbol— lo hace un humano fuera del arnés, que es exactamente donde debe decidirse.

**Alcanza a la coordinadora y al desarrollador.** No es una regla de identidad: es una regla de
comando. `guard-codigo` pregunta *quién* edita; ésta pregunta *qué* se ejecuta. Confundirlas dejaría
al agente autorizado borrando el trabajo de todos los demás (CA-02).

**Cobertura deliberadamente parcial, dicha en voz alta.** Vale lo mismo que para el detector de
escrituras (`AGENTS.md` §13): quedan fuera los **scripts** y los intérpretes que ejecuten git por su
cuenta (`node limpia.mjs`, `make clean`), los alias del shell y cualquier programa que invoque git
sin que su nombre aparezca en el texto del comando. Un hook no puede analizar shell arbitrario de
forma fiable, y perseguirlo produce falsos positivos que terminan con alguien apagando el guard. Es
una barandilla, no una jaula.

**Interacción con REQ-002.** Las consultas de caducidad de REQ-002 (`git log`, `git status`) son
lecturas y no figuran en la lista por defecto: las dos puertas conviven sin contradicción, y CA-16 lo
comprueba como control.

**Fuera de alcance.**
- **Subcomandos destructivos que no están en la lista por defecto**, aunque destruyan un árbol de
  trabajo: medido el 2026-09-06, `git worktree remove --force .` sale **ALLOW** porque no figura en
  `git.prohibidos`. No es un incumplimiento —la lista es mapeo y se amplía con un acto declarado
  (CA-19, CA-34)—, pero queda escrito aquí para que nadie lea la Historia como una promesa universal.
  Si la coordinadora decide meterlo en la lista por defecto, es un cambio de **CA-34** con su fila de
  Historial y su caso de banco, no una interpretación del casado.
- `git push --force` y el resto de operaciones sobre el **remoto**: no destruyen trabajo local y su
  gobierno es del ruleset de `main`, no de un hook local. El mecanismo admite declararlas (CA-19),
  pero no vienen en la lista por defecto.
- Detectar git ejecutado desde un script o un intérprete (ver arriba).
- Recuperar lo ya perdido: esta puerta previene, no restaura.
- No se abre un NFR separado: los umbrales aplicables están cuantificados en CA-26 y CA-27.

## Preguntas abiertas / conflictos
(ninguna.) No hay conflicto con REQ-001 ni con REQ-002: `guard-git` decide sobre el subcomando de git
y no toca la vía `Edit`/`Write`/`MultiEdit` ni la detección del estado terminal; comparte con el
detector de escrituras el **mismo** descuento de comillas y heredocs (CA-07, CA-13), no una segunda
transcripción de esa regla.

**REQ-007 — superficie compartida, sin contradicción (anotado por el analista el 2026-09-05).** Los
Bloques C y G de REQ-007 arreglan **ese mismo** descuento de comillas y heredocs, así que sus
correcciones alcanzan a `guard-git` sin tocarlo. Tres consecuencias, todas de orden y de medición:
1. **`git clean -fd "src"` con los argumentos entrecomillados debe seguir denegándose.** El
   reconocimiento del subcomando de CA-01…CA-06 **no puede depender de que los argumentos vengan
   desnudos**: si el descuento de comillas borra `"src"` del análisis, el token `git clean` sigue
   presente y el veredicto es DENY igual. Es la nota que REQ-007 ya dejó escrita para el desarrollador
   en su propia sección de conflictos; queda también aquí, que es donde vive la puerta afectada.
2. **CA-38 de REQ-007 ciega hoy también a `guard-git`.** Un `git commit -m "documenta <<EOF"` seguido
   de un `git clean -fd` en la misma llamada abre para el detector un heredoc que bash no abre, y todo
   lo que va detrás se descarta. Mientras REQ-007 no aterrice, ese bypass existe **también** para esta
   puerta; no es un criterio nuevo de este REQ —el arreglo es de allí—, pero sí conviene re-correr los
   casos CA-01, CA-06 y CA-07 de aquí **después** de REQ-007 como no-regresión.
3. **Precisión de lectura, no criterio nuevo:** cuando CA-17 y CA-36 dicen que ésta es «la única
   novedad de 1.31.0 encendida por defecto», hablan de **puertas y claves nuevas** que nacen activas.
   REQ-007 también deniega por defecto casos que hoy pasan (clave decorada, destino entrecomillado,
   barra duplicada…), pero eso no es una novedad opcional: es el **cierre de un hueco** de una puerta
   que ya existía y ya estaba encendida. Los dos enunciados conviven; se deja escrito para que nadie
   los lea como contradicción al implementarlos en la misma ventana.
4. **Orden recomendado: REQ-005 antes que REQ-007.** Así el banco de `guard-git` queda escrito y en
   verde sobre el descuento actual, y los arreglos del detector de REQ-007 se miden contra él: si
   alguno rompiera un caso de esta sección, se ve en el acto y se atribuye a REQ-007, que es donde
   está la causa. Al revés, un fallo de `guard-git` sería indistinguible de un fallo del detector.
