## Historia
Como dueño del trabajo que un agente todavía no ha comiteado, quiero que ningún agente —ni siquiera
la sesión coordinadora— pueda ejecutar por `Bash` **ninguno de los subcomandos de git declarados
destructivos en `git.prohibidos`, en cualquiera de sus ortografías** —flag corto o su forma larga
equivalente, agrupado o suelto, con el alias histórico del subcomando—, para que un `git clean` o un
`reset --hard` emitido «para dejar limpio» no borre horas de trabajo que git no puede devolver.

**La promesa es la que la máquina puede sostener, y se escribe así a propósito (precisión del
2026-09-06).** El alcance de esta puerta es **la lista declarada** —que es **mapeo** del proyecto y
se amplía (CA-19, CA-34)—, no «todo comando de git capaz de destruir algo»: `git worktree remove
--force` destruye un árbol de trabajo y hoy **no** está en la lista por defecto, así que pasa, y eso
es una decisión del mapeo, no un fallo de la puerta. Fuera quedan también, y así está declarado, git
ejecutado desde un script o un intérprete. Lo que **no** admite excepción —y es lo que este REQ sí
promete— es que una entrada **ya declarada** se escape por cómo se escribe **en la ortografía de
git**: `git clean --force` borra exactamente lo mismo que `git clean -f`, y `git stash save` es el
alias todavía funcional de `git stash push`. «Cómo se escribe» significa aquí **flag corto o largo y
alias del subcomando**, no la sintaxis del **shell**: lo entrecomillado y el cuerpo literal de un
heredoc van **descontados** antes de que la puerta mire nada (CA-07, CA-13), y por eso un token
entrecomillado o escapado **no se ve** — límite medido, declarado y con ventana de arreglo en
**CA-21.5** (precisión del 2026-09-06, write-back de QA-113).

## Criterios de aceptación

### Bloque A — lo que deniega

- **CA-01** — Dado un proyecto del arnés y la sesión coordinadora, Cuando emite por `Bash` el comando `git clean -fd`, Entonces el hook responde DENY y el motivo nombra el subcomando prohibido y dice por qué (el trabajo sin comitear no es recuperable) y cómo seguir (comitear, o pedirlo al humano).
- **CA-02** — Dado el **mismo** comando emitido por el agente `desarrollador`, Cuando llega la llamada, Entonces el hook responde DENY **igual**: esta puerta es del **comando**, no de la identidad — es justo lo que la distingue de `guard-codigo`, y por eso también alcanza a la coordinadora.
- **CA-03** — Dado cualquier agente, Cuando emite `git reset --hard` o `git reset --hard HEAD~1`, Entonces el hook responde DENY en los dos casos.
- **CA-04** — Dado cualquier agente, Cuando emite `git checkout .` o `git restore .`, Entonces el hook responde DENY en los dos casos.
- **CA-05** — Dado cualquier agente, Cuando emite `git stash` o `git stash push -u`, Entonces el hook responde DENY en los dos casos.
- **CA-06** — Dado cualquier agente, Cuando emite `cd sub && git clean -fd`, `git -C proj reset --hard`, `(git reset --hard)`, `x=$(git stash)` o `git clean -fd | tee log`, Entonces el hook responde DENY en los **cinco**: el subcomando se reconoce **detrás de los separadores y agrupadores que la puerta segmenta** (`&&`, `||`, `|`, `;`, `$(`, acento grave y paréntesis) y de los prefijos que tolera (asignaciones, `sudo`, `command`, `exec`, `time`, `nice`, `env`, `builtin`). **Corrección del 2026-09-06 (write-back de SEC-009):** la redacción anterior decía «el subcomando se reconoce **esté donde esté** dentro del comando», y eso era **falso sobre lo construido** para seis formas ordinarias del shell —medidas por el `auditor-seguridad` en R-002—. Qué se exige para esas seis está en **CA-40**; qué sintaxis del shell sigue sin verse, en «Fuera de alcance». Este criterio no promete universalidad: promete estos cinco casos y los de CA-40.
- **CA-07** — Dado un heredoc **sin citar** cuyo cuerpo contiene la expansión `$(git clean -fd)`, Cuando llega la llamada, Entonces el hook responde DENY: con el delimitador sin citar bash ejecuta de verdad esa sustitución, y aquí se aplica el **mismo descuento** de heredocs y comillas que usa el detector de escrituras.

### Bloque B — lo que NO deniega (controles positivos)

- **CA-08** — [control] Dado cualquier agente, Cuando emite `git stash list` o `git stash show`, Entonces el hook responde ALLOW: son lecturas, no destruyen nada.
- **CA-09** — [control] Dado cualquier agente, Cuando emite `git restore --staged archivo.ts`, Entonces el hook responde ALLOW: saca del índice, no toca el árbol de trabajo.
- **CA-10** — [control] Dado cualquier agente, Cuando emite `git clean -n` o `git clean --dry-run`, Entonces el hook responde ALLOW: enumeran lo que borrarían y no borran nada.
- **CA-11** — [control] Dado cualquier agente, Cuando emite `git reset --soft HEAD~1` o `git reset archivo.ts`, Entonces el hook responde ALLOW: sin `--hard` no se pierde el árbol de trabajo.
- **CA-12** — [control] Dado cualquier agente, Cuando emite `git checkout rama`, `git checkout -b rama` o `git restore --source=HEAD~1 archivo.ts`, Entonces el hook responde ALLOW: sólo la forma con `.` arrasa el árbol entero.
- **CA-13** — [control, el texto no es el comando] Dado cualquier agente, Cuando emite `git commit -m "no uses git clean"`, `git commit -m 'reset --hard revertido'` o un heredoc **citado** (`<<'EOF'`) cuyo cuerpo dice `git clean -fd`, Entonces el hook responde ALLOW en los tres: lo entrecomillado y el cuerpo literal de un heredoc se descuentan antes de mirar el comando.
- **CA-14** — [control] Dado cualquier agente, Cuando emite `github clone x`, `gitk`, `mygit clean` o `legit clean`, Entonces el hook responde ALLOW: `git` se reconoce como **token** de comando, no como subcadena.
- **CA-15** — [control] Dado cualquier agente, Cuando emite `echo "git clean"` o `grep -r "git stash" .`, Entonces el hook responde ALLOW.
- **CA-16** — [control, no regresión] Dado el conjunto de comandos de las secciones existentes del banco que hoy responden ALLOW y contienen `git` (por ejemplo `git status`, `git log`, `git diff`, `git add`, `git commit`), Cuando corren contra la candidata, Entonces todos siguen en ALLOW.

### Bloque C — el manifiesto: mecanismo aquí, mapeo allí

- **CA-17** — Dado un manifiesto **sin** el bloque `git`, Cuando llega `git clean -fd`, Entonces el hook responde DENY: `git.activo` vale `true` por defecto y ésta es **la única novedad de 1.31.0 encendida por defecto**. El estado «manifiesto presente pero **ilegible**» no es «sin bloque `git`» y lo gobierna **CA-42**.
- **CA-18** — [control] Dado `git.activo: false`, Cuando llegan los comandos de CA-01 a CA-06, Entonces el hook responde ALLOW en todos: el proyecto puede apagar la puerta con un acto explícito.
- **CA-19** — Dado `git.prohibidos: ["push --force"]` (lista propia que **sustituye** a la de por defecto), Cuando llega `git clean -fd`, Entonces el hook responde ALLOW; y Cuando llega `git push --force origin main`, Entonces responde DENY: la lista es del proyecto, la comparación es del arnés.
- **CA-20** — Dado `git.prohibidos: []`, Cuando llegan los comandos de CA-01 a CA-06, Entonces el hook responde ALLOW en todos: una lista vacía es una decisión declarada, no un error.
- **CA-21** — [la regla de casado] Dado un `git.prohibidos` cuyas entradas tienen la forma `subcomando [token...]`, Cuando llega un comando de git, Entonces la entrada casa **si y sólo si** el subcomando coincide y **todos** los tokens de la entrada **casan** contra ese segmento, **en cualquier orden**. Y «casar» **no** es «la cadena aparece»: depende del **tipo** del token (precisión del 2026-09-06, write-back de QA-110) — un token de **opción** (el que empieza por `-`) casa sólo contra un argumento que el comando **trate como opción**, mientras que un token **literal** (`.`, `save`, una ruta) casa contra cualquier argumento igual, sea opción u operando. **El `-` solo es literal**, no opción: en git es un operando (`git checkout -` es «la rama anterior»), y así lo trata el código —medido el 2026-09-06: con la regla propia `checkout -`, `git checkout -- -` sale **DENY**—. La distinción no es teórica: es la que hace que `git clean -- -f` pase y `git checkout -- .` no. Con **cinco** precisiones que la regla declara y el banco mide:
  1. **Flags cortos, por letra.** Un token que es un flag corto casa cuando **todas sus letras** aparecen en un **mismo grupo** de flags cortos del comando: `-f` casa con `-f`, `-fd`, `-fdx` y `-ffd`, y **no** casa con `-n` ni con `-d`. Así, Dado `clean -f`, Cuando llega `git clean -fd`, Entonces **DENY**, y Cuando llega `git clean -n` o `git clean --dry-run`, Entonces **ALLOW** (CA-10 se conserva intacto).
  2. **Ortografías equivalentes de un token declarado (write-back de QA-101, 2026-09-06).** Un token de la entrada casa **también** cuando el comando lo escribe en **otra ortografía de la misma opción o del mismo subcomando**, según una tabla del **arnés** (mecanismo, no mapeo) que hoy declara **exactamente**: `-f` ≡ `--force`, `-d` ≡ `--directory` (en `clean`), **`-x`** —listado **sin forma larga equivalente**: no la tiene en la tabla y no la necesita, porque casa por letras (precisión 1); medido el 2026-09-06, `clean -x` deniega `git clean -x` y `git clean -xdf` y deja pasar `git clean -f`—, `-n` ≡ `--dry-run`, `-u` ≡ `--include-untracked`, `--all` ≡ `-a` (en `stash`), **`-S` ≡ `--staged` y `-W` ≡ `--worktree` (en `restore`)** —las dos últimas, write-back de QA-110 del 2026-09-06: el código ya las implementa y la tabla no las listaba, de modo que el banco no probaba lo que existe—, y el **alias histórico** `stash save` ≡ `stash push`. Así, Dado `clean -f`, Cuando llegan `git clean --force`, `git clean --force -d` o `git clean -d --force`, Entonces **DENY** en los tres —medido el 2026-09-06 **sobre la candidata `40312c6`**, que es su par fail-before: allí los tres salían **ALLOW**, porque el casado comparaba los flags cortos por letra y **saltaba todo argumento que empezara por `--`**—; y Dado `stash push`, Cuando llega `git stash save "wip"`, Entonces **DENY**. **Controles que no pueden moverse:** Dado `clean -f`, Cuando llegan `git clean -n` o `git clean --dry-run`, Entonces **ALLOW** (CA-10 intacto: la equivalencia mapea cada token a **sus** ortografías, y `--dry-run` es la de `-n`, no la de `-f`); y Dado `stash`, Cuando llegan `git stash list` o `git stash show`, Entonces **ALLOW** (CA-08 intacto: `list` y `show` no son alias de `push`). **La excepción declarada de `restore`, ahora también en su forma corta:** la entrada `restore .` **no** casa cuando el comando lleva `--staged` **y no** lleva `--worktree`, porque esa forma sólo rehace el índice y deja el árbol de trabajo intacto (es lo que CA-09 ya declara con la forma larga). Con `-S` ≡ `--staged` en la tabla, la excepción alcanza también a la forma corta: Dado `restore .`, Cuando llega `git restore -S .`, Entonces **ALLOW** —verificado el 2026-09-06 en un repositorio desechable: el archivo conserva su contenido sin comitear—; y Cuando llega `git restore -W .`, Entonces **DENY**, porque `--worktree` sí arrasa el árbol. **Lo que queda fuera de la tabla no casa, y eso es declarado, no accidental:** la tabla es del mecanismo y se amplía con un caso del banco por cada entrada nueva; una ortografía que no esté en ella pasa, exactamente como pasa un subcomando que no está en la lista.
  3. **Una entrada sin tokens casa sólo con el subcomando desnudo.** Dado `stash`, Cuando llega `git stash` o `git stash -u` —ningún token **posicional** detrás; los flags no cuentan como posicional—, Entonces **DENY**; y Cuando llega `git stash list` o `git stash show`, Entonces **ALLOW** (CA-08 se conserva intacto).
  4. **Fin de opciones: detrás de `--` no hay opciones, sólo operandos (write-back de QA-110, 2026-09-06).** El separador `--` de git **termina la lista de opciones**: todo lo que va detrás es un operando —una ruta, un pathspec—, por mucho que empiece por guiones. Por eso un token de **opción** de la entrada **deja de buscarse** a partir del `--`, mientras que un token **literal** se sigue buscando también detrás. Así, Dado `clean -f`, Cuando llegan `git clean -- -f` o `git clean -- --force`, Entonces **ALLOW** en los dos: ahí `-f`/`--force` es el **nombre de un archivo**, y el comando sólo alcanzaría a un archivo llamado literalmente así —y sólo con `clean.requireForce=false`, porque con la configuración por defecto git se niega (`fatal: clean.requireForce is true and -f not given`)—; Dado `reset --hard`, Cuando llega `git reset -- --hard`, Entonces **ALLOW**: ahí `--hard` es un pathspec y el comando deja el árbol y el índice **exactamente igual**. Los dos casos están **verificados ejecutándolos** en un repositorio desechable el 2026-09-06, no razonados. **El control que no puede moverse:** Dado `checkout .`, Cuando llega `git checkout -- .`, Entonces **DENY**, porque `.` es un token **literal** y el fin de opciones no lo apaga — `git checkout -- .` arrasa el árbol exactamente igual que `git checkout .`, y es además su forma canónica. Sin esta precisión el criterio afirmaría lo contrario de lo construido **y de lo correcto**: por la regla de «todos los tokens presentes», el `-f` de `git clean -- -f` **está presente** y la entrada tendría que casar.
  5. **La sintaxis del shell va descontada antes: un token entrecomillado o escapado no llega al análisis (precisión del 2026-09-06, write-back de QA-113).** Antes de que esta regla mire nada, `guard-git` aplica el **mismo** descuento de comillas y heredocs que el detector de escrituras (CA-07, CA-13), y lo hace a propósito: sin él, `git commit -m "no uses git clean"` sería un `git clean`. Ese descuento **borra el contenido de cada par de comillas** y no distingue un mensaje de un flag, así que un token escrito **entrecomillado o escapado** —sea **flag** o **subcomando**— desaparece del comando antes del casado y la entrada **no casa**. Los controles que fijan esa conducta, **medidos el 2026-09-06 sobre `430f4fd`** con canario positivo (`git clean -fd` → DENY) y negativo (`ls -la` → ALLOW) en la misma tanda, e idénticos a través de `guard.sh` y llamando directo a `guard-git.sh`:
     - **Seis formas que hoy salen ALLOW** y que con los argumentos desnudos saldrían DENY: `git clean "-f"`, `git checkout "."`, `git reset "--hard"`, `git "clean" -f`, `git clean \-f` y `git stash "save" wip`. Para bash, `git clean "-f"` **es** `git clean -f` y borra exactamente lo mismo: lo que falla no es la semántica de git, es que el texto no llega.
     - **Los dos controles que no se mueven:** `git clean -fd "src"` —el **operando** entrecomillado— sigue en **DENY**, y `git clean -f` desnudo sigue en **DENY**. Entrecomillar un operando no desarma nada; entrecomillar el token, sí.
     - **Borde medido, para que nadie lea la familia como uniforme:** `git clean --force""` y `git clean -f""` salen **DENY**, mientras `git clean --for"ce"` sale **ALLOW** — el descuento borra el par de comillas y lo que queda pegado se re-une o no según dónde caiga la comilla. Por eso el límite se enuncia como «lo entrecomillado no se ve», y **no** como «las comillas apagan la puerta».
     - **Alcance del límite, con dueño y ventana: no es de este REQ.** El descuento es **compartido** —no una segunda transcripción de esa regla (ver «Preguntas abiertas / conflictos»)— y su arreglo está asignado al **Bloque C de REQ-007 (CA-14…CA-18), ventana 1.32.0**. Cuando aterrice, los seis comandos de arriba pasarán a **DENY** y los casos del banco que hoy fijan su ALLOW **cambiarán de veredicto en voz alta**, que es exactamente lo que se le pide a un hueco declarado: que su cierre se note.
     - **No es una regresión de esta ventana, sino un hueco heredado.** Medido en la línea base, **v1.30.3 publicada** deja pasar `echo x > "src/a.ts"` por esta misma causa (y deniega `echo x > src/a.ts`), y la candidata se comporta **igual** en esa vía. Antes de `guard-git` los seis comandos pasaban **todos**, con comillas y sin ellas: la puerta nueva no abre nada que estuviera cerrado, sólo cierra menos de lo que su enunciado prometía.

  **Los tres veredictos que esta precisión declara son cambios respecto de la implementación anterior de esta misma ventana, no respecto de la versión publicada.** Medidos por el `qa-tester` el 2026-09-06 comparando 103 comandos entre la candidata `40312c6` y la candidata `22636cb` (`docs/qa/1.31.0.md` §5, QA-110): `git clean -- -f`, `git reset -- --hard` y `git restore -S .` pasan de **DENY** a **ALLOW**; las otras 11 transiciones van de `allow` a `deny` y son el arreglo de QA-101. Contra **v1.30.3 publicada** ninguno de los tres es un cambio de conducta: allí `guard-git` no existía y los tres salían ALLOW por ausencia de puerta. En consecuencia, **no** son regresiones y no contradicen a CA-31: los tres son controles positivos que pasan también contra la instalación estable anterior.

  Y como control del reconocimiento: Dado `reset --hard`, Cuando llegan `git reset --hard` y `git reset HEAD~1 --hard` (el token en otra posición del mismo segmento), Entonces **DENY** en los dos; y Dado `clean -f`, Cuando llega `git clean -fd "src"` con el **operando** entrecomillado, Entonces **DENY**: entrecomillar un **operando** no desarma el reconocimiento, porque lo que el descuento borra es ese operando y el subcomando con sus flags sigue en el texto. **Hasta dónde llega esta frase y hasta dónde no (corrección del 2026-09-06, write-back de QA-113):** vale para el **operando**, y **no** para el token. Si lo entrecomillado o escapado es el **flag** o el **subcomando**, el descuento sí lo borra y la entrada no casa — es el límite declarado, medido y con ventana de arreglo de la precisión **5**. La redacción anterior («el reconocimiento … no depende de que los argumentos vengan desnudos» y «el descuento … no puede borrar el segmento del comando») generalizaba de más y era **falsa sobre lo construido** para seis formas ordinarias.
- **CA-22** — Dado un entorno sin `jq` o un proyecto sin `.arnes/config.json`, Cuando llega `git clean -fd`, Entonces el hook es **inerte** y no bloquea, igual que el resto: el cambio no introduce ninguna dependencia dura nueva ni convierte una carencia de tooling en un bloqueo. **Este criterio cubre la ausencia, no la avería:** el caso «manifiesto **presente pero ilegible**» **no** es inerte y lo gobierna **CA-42** (write-back de SEC-009/SEC-010, 2026-09-06). Antes del 2026-09-06 ese tercer estado no estaba declarado en ningún criterio, y la conducta medida —permitir— contradecía el aviso que el propio arnés emite.

### Bloque D — integración, orden y coste

- **CA-23** — Dado `hooks/guard.sh`, Cuando se revisa el orden de invocación, Entonces `guard-git` corre **antes** que `guard-codigo` y `guard-completado`.
- **CA-24** — Dado un comando que es a la vez `git clean -fd` y una escritura sobre código protegido, Cuando llega la llamada, Entonces el motivo de la denegación es el de **git** (se verifica el texto): la denegación es final y los otros dos guardianes no llegan a correr.
- **CA-25** — [control] Dado un comando que `guard-git` permite y que `guard-codigo` debe denegar (`echo x > src/generated.ts` desde la coordinadora), Cuando llega la llamada, Entonces el hook responde DENY con el motivo de **código protegido**: interponer el guardián nuevo no apaga a los que ya estaban.
- **CA-26** — Dado un comando de Bash que **no** contiene el token `git` (`ls -la`, `npm test`), Cuando pasa por `guard.sh`, Entonces `guard-git` **no lee el manifiesto ni arranca `jq`**: el número de invocaciones de `jq` es el mismo que en **v1.30.3 publicada** (la línea base de no-regresión de 1.31.0; medido con un `jq` instrumentado en el `PATH` que registra sus llamadas). **Precisión de medición (2026-09-06, write-back de QA-104):** lo exigible aquí es que **`guard-git` no aporte ninguna invocación** —su registro propio queda vacío—; el conteo **agregado** del camino común lo gobierna **CA-59 de REQ-007**, porque la lectura del manifiesto que SEC-005 adelantó en `guard-codigo.sh` añade **+1** proceso por comando (2 contra 1 de v1.30.3) que no es de este REQ. Sin esta precisión, el criterio afirmaría en agregado algo que la medida desmiente.
- **CA-27** — Dado un comando que **sí** contiene `git`, Cuando `guard-git` lo evalúa, Entonces añade como máximo **1** lectura del manifiesto por invocación, la evaluación tarda **menos de 200 ms** y la invocación completa del hook responde en **menos de 5 s**.
- **CA-28** — Dado `hooks/guard-git.sh`, Cuando se ejecuta directamente (no `source`), Entonces hace su propio preludio y decide igual que dentro de `guard.sh` — producción y banco ejecutan **la misma función**, no dos copias que puedan desfasarse.
- **CA-29** — Dado el índice de git del PR, Cuando corre el paso de bits de ejecución del CI, Entonces `hooks/guard-git.sh` figura en modo `100755`, igual que el resto de puntos de entrada.

## Notas / alcance

**Origen — un incidente medido.** En un proyecto real se perdieron **~52 archivos de trabajo sin
comitear** en un incidente. La causa de fondo no es el descuido de nadie: **el trabajo de un
subagente no es atómico para git**. Un agente limpia «su» árbol y arrasa el de otro; un comando que
en manos de una persona es rutinario, dentro de una sesión con varios agentes en marcha es
irreversible y silencioso. La regla que funcionó fue comitear tras cada aterrizaje, y esta puerta es
la mitad que la máquina puede sostener.

**Por qué ésta sí nace encendida, y sólo ésta.** Las demás novedades de 1.31.0 cambian **cómo se
juzga** algo y por eso nacen apagadas: encenderlas por sorpresa rompería proyectos que no las
pidieron. Ésta impide una operación **destructiva e irreversible** cuyo valor legítimo dentro de una
sesión de agentes es casi nulo, y cuyo coste cuando falla no se puede deshacer. Un proyecto que la
necesite la apaga con un acto explícito (CA-18) o cambia la lista (CA-19). El caso legítimo —limpiar
de verdad el árbol— lo hace un humano fuera del arnés, que es exactamente donde debe decidirse.

**Alcanza a la coordinadora y al desarrollador.** No es una regla de identidad: es una regla de
comando. `guard-codigo` pregunta *quién* edita; ésta pregunta *qué* se ejecuta. Confundirlas dejaría
al agente autorizado borrando el trabajo de todos los demás (CA-02).

**Cobertura deliberadamente parcial, dicha en voz alta.** Vale lo mismo que para el detector de
escrituras (`AGENTS.md` §13): quedan fuera los **scripts** y los intérpretes que ejecuten git por su
cuenta (`node limpia.mjs`, `make clean`), los alias del shell y cualquier programa que invoque git
sin que su nombre aparezca en el texto del comando. Un hook no puede analizar shell arbitrario de
forma fiable, y perseguirlo produce falsos positivos que terminan con alguien apagando el guard. Es
una barandilla, no una jaula.

**Excepción de proceso: una cuarta vuelta autorizada, con su razón y su fecha (2026-09-06).** Este
REQ **agotó sus tres vueltas** del bucle dev↔QA que `AGENTS.md` §6 permite (QA-101 → QA-110 →
QA-113), y el tope **no se reinicia con cada hallazgo nuevo**. Al llegar el veto del
`auditor-seguridad` en R-002, las salidas previstas eran cerrar con el residual declarado o pasar el
REQ a `bloqueado` y escalar. El propietario tenía delegada la decisión y **la coordinadora autorizó
una vuelta extra** —la cuarta— por tres razones que se escriben para que la excepción se pueda juzgar
y no se convierta en costumbre:
1. **La puerta nace encendida.** A diferencia del resto de 1.31.0, `guard-git` se activa sola en
   **todos** los proyectos que instalen la versión (CA-17). Cerrar con residual aquí no deja un
   límite en un documento: deja una puerta que promete y no cumple funcionando en proyectos que no
   la pidieron.
2. **El arreglo estaba nombrado y acotado por el propio auditor.** SEC-009 y SEC-010 llegan con la
   causa en el código, la lista de formas medidas y la recomendación concreta; no es una
   investigación abierta, es un cambio delimitado con su par fail-before.
3. **Una puerta que promete de más es peor que una apagada**, porque se confía en ella. Es el mismo
   argumento con el que SEC-005 se consideró más grave que la ausencia de manifiesto.

**Lo que la excepción NO hace:** no reinicia el contador ni crea un tope nuevo. Si esta cuarta vuelta
no cierra SEC-009 y SEC-010, el REQ va a `bloqueado` y la decisión vuelve al propietario, sin
discusión. Queda registrada en el Historial de cambios con su fila propia, que es donde una
excepción de proceso se puede auditar.

**Interacción con REQ-002.** Las consultas de caducidad de REQ-002 (`git log`, `git status`) son
lecturas y no figuran en la lista por defecto: las dos puertas conviven sin contradicción, y CA-16 lo
comprueba como control.

  `git.prohibidos`. No es un incumplimiento —la lista es mapeo y se amplía con un acto declarado

  `git ${cmd} .`— (declarado el 2026-09-06; lo dejó pendiente el `desarrollador` en su entrega
  anterior y hasta hoy **no estaba escrito en ningún sitio**, que es exactamente la clase de hueco
  que este REQ se ha comprometido a nombrar). La puerta lee el **texto** del comando, y el valor de
  la variable sólo existe **al expandirla**: verlo exigiría **evaluar shell**, es decir, ejecutar
  aquello que se está juzgando —lo que un hook `PreToolUse` no puede hacer y no debe intentar—. Lo
  que la puerta ve es el token literal `$G`, que no casa con ninguna entrada de `git.prohibidos`, y
  por eso el veredicto es **ALLOW**. La forma de una sola línea (`G=clean git $G -f`) tampoco cambia
  nada: el bucle de prefijos tolera la asignación (`*=*`), de modo que el segmento **sí** se examina
  y sigue siendo `$G` lo que falta, no el segmento. Como el resto de esta lista, exige **intención**:
  nadie escribe `G=clean; git $G -f` por descuido. Si algún día se quisiera cerrar, no se cierra
  ampliando el casado, sino **denegando la forma** (un `git` cuyo primer argumento contenga `$`), y
  eso es un criterio nuevo con su medición de falsos positivos, no una interpretación de CA-21.
- Detectar git ejecutado desde un script o un intérprete (ver arriba).
- Recuperar lo ya perdido: esta puerta previene, no restaura.
- No se abre un NFR separado: los umbrales aplicables están cuantificados en CA-26 y CA-27.

Bloques C y G de REQ-007 arreglan **ese mismo** descuento de comillas y heredocs, así que sus
correcciones alcanzan a `guard-git` sin tocarlo. Tres consecuencias, todas de orden y de medición:
1. **`git clean -fd "src"` con el *operando* entrecomillado debe seguir denegándose** — y ahí acaba
   lo que esta nota sostiene (corregido el 2026-09-06 por QA-113). Si el descuento de comillas borra

   ya dejó escrita para el desarrollador en su propia sección de conflictos; queda también aquí, que
