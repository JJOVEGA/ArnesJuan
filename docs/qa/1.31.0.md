## 4. Hallazgos

### QA-101 — `git clean --force` y `git stash save` atraviesan la puerta nueva
**REQ-005 · clase `contrato` · severidad alta · dueño `desarrollador`**

**Reproducción**

```
$ printf 'git clean --force' | jq -Rs '{hook_event_name:"PreToolUse",tool_name:"Bash",
    cwd:env.CLAUDE_PROJECT_DIR,tool_input:{command:.}}' | hooks/guard-git.sh
(salida vacía)          -> allow
```

Igual con `git clean --force -d`, `git clean -d --force` y `git stash save "wip"`.
Control positivo en la misma corrida: `git clean -f`, `git clean -fd`, `git clean -xdf`,
`git stash push -u` → **DENY**. Control negativo: `git clean --dry-run`, `git stash list`
→ **allow**, como debe ser.

**Esperado vs observado**
`git clean --force` borra exactamente lo mismo que `git clean -f`, y `git stash save` es
el alias histórico —todavía funcional— de `git stash push`, que sí se deniega. Esperado:
DENY en los tres. Observado: ALLOW en los tres.

**Causa**
`arnes_casa_token` (`hooks/guard-git.sh`) compara los flags **cortos por letras** y salta
explícitamente todo argumento que empiece por `--`:

```
case "$a" in
  --*|-) continue ;;
```

La lista por defecto (`hooks/lib.sh:71`) declara `"clean -f"`, una sola ortografía. La
forma larga del mismo flag no está en ninguna regla, y el alias `save` tampoco.

**Por qué es `contrato`**
La Historia de REQ-005 afirma que «ningún agente —ni siquiera la sesión coordinadora—
pueda ejecutar por `Bash` un subcomando de git que destruye el árbol de trabajo». Eso es
falso sobre lo construido para tres formas ordinarias, no exóticas. Se cierra cuando el
código las cubra **o** cuando el REQ declare por escrito el límite de la regla (que sólo
alcanza las ortografías declaradas) y añada el criterio correspondiente.

**Casos de banco añadidos:** `QA-101 'git clean --force' -> deny`, `QA-101 'git clean
--force -d' -> deny`, `QA-101 'git stash save "wip"' -> deny`, más dos controles.

### QA-102 — la sección declarada que no existe no rota nada, pero tampoco lo dice
**REQ-004 CA-09 · clase `contrato` · severidad media · dueño `desarrollador`**

**Reproducción**

Proyecto con `rotacion.activo: true`, `umbral_bytes: 1000` y el artefacto
`{"glob":"requirements/REQ-*.md","seccion":"## Historial","conservar_entradas":20}`,
mientras la sección real del documento es `## Historial de cambios`; REQ de ~14 KB con
60 entradas. Se emite una parada (`hooks/stop.sh` con `{"hook_event_name":"Stop"}`).

**Esperado vs observado**

| | Esperado (CA-09) | Observado |
|---|---|---|
| El documento no cambia | sí | **sí** ✔ |
| `arnes_warn` que nombre el archivo y la sección declarada | sí | **stderr vacío** ✘ |
| El bloque derivado refleja «sección declarada no encontrada» | sí | **nada** ✘ |

**Causa**
`hooks/rotar-artefactos.sh`, tras partir el documento:

```
[ "$fase" -ge 1 ] || return 0            # el documento no tiene esa seccion: no se toca
```

Un `return 0` mudo, antes de cualquier aviso. `hooks/estado-derivado.sh` no tiene ninguna
referencia a la rotación, así que la segunda mitad del criterio tampoco puede cumplirse.

**Por qué importa**
Es el caso que la propia DoR midió y el criterio nombra: «un artefacto declarado que no
existe es un error de mapeo que hay que ver, no un acierto silencioso». Un proyecto que
escriba mal el nombre de la sección cree que rota y no rota, sin una sola señal.

**Caso de banco añadido:** `QA-102 CA-09: la seccion declarada no encontrada emite
arnes_warn`.

**Caso de banco añadido:** `QA-103 el motivo del techo imprime el maximo en BYTES...`.

### QA-104 — el camino común de `Bash` paga un proceso más que en 1.30.3
**REQ-007 (SEC-005) · clase `contrato` · severidad media · dueño `desarrollador` + analista**

**Reproducción** — con un `jq` instrumentado primero en el `PATH` que cuenta invocaciones
y delega en el real:

| Entrada | Candidata | v1.30.3 |
|---|---|---|
| `Bash: ls -la` | **2** procesos `jq` | 1 |
| `Bash: npm run build` | **2** | 1 |
| `Bash: git status` | **2** | 1 |
| `Edit` fuera de los globs | 3 | 3 |

Reloj sobre 200 invocaciones de `guard.sh` con `ls -la`: candidata **26,0 ms/inv**,
v1.30.3 **16,1 ms/inv** → **+9,9 ms** en Linux/WSL2.

**Causa** — en `hooks/guard-codigo.sh`, `arnes_parse_manifest` se movió *delante* del
corte temprano:

```
+ arnes_parse_manifest
+ arnes_deny_manifiesto_roto ...
  [ -n "$objetivo" ] || return 0   # no es código de app -> permitir
- arnes_parse_manifest
```

Es **consecuencia directa y necesaria** de SEC-005 (CA-51): sin leer el manifiesto no se
puede distinguir «no es código protegido» de «no sé qué es código protegido». No es un
descuido, es un coste.

**Por qué es `contrato` y no sólo un dato**
Los criterios de esta ventana afirman repetidamente lo contrario: REQ-003 CA-22 («no añade
ningún proceso a esa ruta — 0 forks añadidos respecto a v1.30.3, medido con un `jq`
instrumentado en el `PATH`»), REQ-007 CA-44 y CA-48 («coste: 0 procesos nuevos/añadidos»)
y CA-50(d). Medido en conjunto, la candidata añade **uno** por cada comando `Bash`, que es
la llamada más frecuente que existe. En Linux cuesta 10 ms; en la plataforma del
desarrollador —donde `AGENTS.md` §2 cifra cada fork en **1,2–6 s**— ese mismo proceso es
el orden de magnitud que el arnés lleva tres versiones peleando.

No pido revertir SEC-005: pido que el coste **se declare** en un criterio (write-back del
analista) y, si se puede, que se pague sólo cuando haga falta. Mientras el REQ diga «0
procesos añadidos» y la medición diga «+1», hay deriva.

*(No se añade caso de banco: contar procesos requiere instrumentar el `PATH` y el banco no
tiene hoy ese armazón fuera de la sección de rendimiento.)*

### QA-105 — con el manifiesto roto, la salida que el propio motivo recomienda está denegada
**REQ-007 (SEC-005) · clase `instrumento` · severidad media · dueño `desarrollador`**

**Reproducción** — proyecto con `.arnes/config.json` = `{"agentes":{,}`:

| Llamada | Resultado |
|---|---|
| `Write` a `docs/notas.md` (ruta no protegida), coordinadora | DENY |
| `Write` a `.arnes/config.json` con `agent_type: desarrollador` | **DENY** |
| `Bash: printf "{}" > .arnes/config.json`, `desarrollador` | **DENY** |
| `Bash: ls -la` | allow |
| `Bash: node fix.mjs` | allow (vía de escape ya declarada en `AGENTS.md` §13) |

El motivo del DENY dice: *«Salidas: corrige el JSON (pruebalo con `jq -e .
.arnes/config.json`) o borra el archivo…»*. Ninguna de las dos se puede hacer desde la
sesión: las dos son escrituras y las dos están denegadas, para **todos** los agentes.

**Esperado vs observado**
El fail-closed es correcto y no lo discuto. Lo que falla es que el remedio que el propio
mensaje ofrece es inalcanzable por la vía que el mensaje sugiere, y el REQ no lo dice. Un
proyecto con una coma de más queda con todo `Edit`/`Write` bloqueado hasta que una persona
edite el archivo fuera de la sesión.

**Salidas posibles** (decisión del desarrollador, no mía): permitir la escritura de
`.arnes/config.json` al agente de código aun con el manifiesto roto —es el único archivo
cuya reparación devuelve la capacidad de medir—, o reescribir el motivo para que nombre la
vía real (arreglarlo fuera de la sesión / desde el editor).

### QA-106 — `veredictos.exigir_fecha` con un valor no booleano apaga la puerta en silencio
**REQ-002 · clase `instrumento` · severidad baja · dueño `desarrollador`**

**Reproducción** — REQ crítico con `QA: aprobado` y `Seguridad: aprobado` **sin fecha**,
listo para cerrar:

| `veredictos.exigir_fecha` | Veredicto | Aviso |
|---|---|---|
| `true` | DENY (correcto) | — |
| `false` / clave ausente | allow (correcto) | — |
| `"true"` (cadena) | **allow** | **ninguno** |
| `1` | **allow** | ninguno |
| `[]`, `null` | allow | ninguno |

Un proyecto que escriba `"exigir_fecha": "true"` cree que la exigencia está activa y no lo
está, sin una sola señal. El arnés ya resuelve bien este mismo caso en
`limites.bash_max_analisis`, que **avisa** cuando el valor no es un número JSON
(«una cadena como "999999" no lo es»). La asimetría es lo que sorprende.

Falla en abierto respecto de la intención del proyecto, pero **no** respecto de 1.30.3:
sin el opt-in la conducta es la de siempre, así que no reabre nada. Por eso `instrumento`.

### QA-107 — un número JSON en forma exponencial o decimal ni recorta ni avisa
**REQ-007 CA-54 · clase `instrumento` · severidad baja · dueño `desarrollador`**

| `limites.bash_max_analisis` | Techo efectivo | Aviso |
|---|---|---|
| `131073`, `4294967296`, `99999999999999999999` | 131072 (máximo) | sí, correcto |
| `"999999"`, `"131072"`, `true`, `[]` | defecto | sí, «no es un numero» |
| **`1e9`** (número JSON válido = 1 000 000 000) | defecto | **ninguno** |
| **`1.5`** | defecto | **ninguno** |

Comando de 70 KB → DENY en los cuatro últimos: **falla cerrado**, no hay riesgo. Lo que
falta es el aviso: `1e9` no es ni «supera el máximo» (no recorta a 131072) ni «no es un
número» (jq dice que sí lo es), y cae por el hueco entre las dos ramas.
