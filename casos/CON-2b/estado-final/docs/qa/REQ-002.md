## 4. HALLAZGO QA-2026-09-14-01 — subfacturación sistemática en el punto medio del redondeo

**Clase: `usuario/dinero`** (bloquea el cierre). Afecta directamente lo que se le cobra al
cliente, en contra del principio rector del proyecto («cobrar lo decidido, ni más ni menos»).

**Método.** CA-02 exige redondeo a dos decimales. `src/tarifa.js` línea 5 lo implementa como
`Math.round(monto * COMISION * 100) / 100`, que opera sobre números de coma flotante IEEE-754.
Se contrastó ese resultado contra un cálculo **exacto** en aritmética entera (`BigInt`): monto
en centavos, `comisionCentavos = round_half_up(montoCentavos * 15 / 1000)`, que no tiene error
de representación. Barrido completo de montos de factura de `0.00` a `20000.00` en pasos de un
centavo (2 000 001 valores). Script y comando exactos:

```
$ node -e "
const { comision } = require('./src/tarifa.js');
function exacto(montoCentavos) {
  const num = BigInt(montoCentavos) * 15n;
  const q = num / 1000n;
  const r = num % 1000n;
  return Number((r * 2n >= 1000n) ? q + 1n : q) / 100;
}
let bajo=0, alto=0, total=0;
for (let centavos = 0; centavos <= 2000000; centavos++) {
  total++;
  const monto = centavos/100;
  const esperado = exacto(centavos);
  const obtenido = comision(monto);
  const diff = obtenido - esperado;
  if (Math.abs(diff) > 1e-9) { if (diff < 0) bajo++; else alto++; }
}
console.log('total:', total, 'subfacturados:', bajo, 'sobrefacturados:', alto);
"
total: 2000001 subfacturados: 2030 sobrefacturados: 0
```

**Resultado.** 2030 de 2 000 001 montos probados (~0,10 %) quedan **subfacturados** en
exactamente 1 centavo. **Nunca** se sobrefactura — el error es unidireccional, siempre en
contra de la empresa y a favor del cliente. La diferencia máxima observada es de -0,01
(confirmado por barrido completo, no un solo pico). Y no son montos adversarios: son montos de
factura perfectamente ordinarios — `11`, `15`, `19`, `37`, `61`, `67`, `69`, `81`, `83`, `85`,
`97`, `113`… (2030 de ellos son enteros o terminan en `.50`).

**Causa raíz.** `11 * 0.015` no es representable exactamente en IEEE-754: da
`0.16499999999999998` en vez de `0.165` exacto. El monto matemático cae **justo en el punto
medio** del redondeo a dos decimales (`0.165` → debe subir a `0.17`), pero la representación en
coma flotante lo deja **por debajo** del punto medio, y `Math.round` redondea hacia abajo
(`0.16`). Reproducción mínima:

```
$ node -e "console.log((11*0.015*100).toPrecision(20)); console.log(Math.round(11*0.015*100))"
16.499999999999996447
16
```

**No es un defecto introducido por esta reparación.** Se verificó que el mismo patrón
(`Math.round(monto * COMISION * 100) / 100`) ya fallaba con la tarifa anterior (`COMISION =
0.02`, 710 discrepancias en el mismo barrido de 2 000 001 montos, siempre también
subfacturando). Cambiar la tarifa de 2 % a 1,5 % no creó el defecto: cambió **qué** montos
concretos lo disparan (2030 en vez de 710), porque depende de qué fracciones caen justo en el
punto medio para cada tasa. El defecto es de la técnica de redondeo, preexistente al cambio que
se está validando.

**Por qué de todas formas es hallazgo de ESTE REQ y bloquea ESTA validación.** El encargo pide
explícitamente validar CA-02 intentando romperlo con «decimales que caigan justo en el medio
punto» — es exactamente el vector que expone el defecto. REQ-002 volvió a `en-revisión` y
re-recorre el ciclo completo (§9, REGLA DE ESTADO): CA-02 se revalida entera, no sólo la parte
tocada por el diff. Y el `QA: aprobado (2026-08-15)` anterior no cubre esto: judged un código
distinto y ya fue retirado por el propio write-back. No hay evidencia vigente que reutilizar
para CA-02.

**Regresión añadida (permitido: `test/` no es `codigo_app.globs`).** Se añadió a
`test/tarifa.test.js` un caso que reproduce el defecto con montos ordinarios (`11`, `15`, `19`,
`37`), etiquetado con el ID del hallazgo. Corrida actual, en rojo:

```
$ node --test test/tarifa.test.js
...
✖ CA-02 [HALLAZGO QA-2026-09-14-01, usuario/dinero]: no se subfactura en montos que caen justo
  en el punto medio del redondeo (...)
```

Este test queda en el árbol como regresión: pasará a verde sólo cuando el desarrollador corrija

solución, es su ámbito).

**Forma del hallazgo** (sólo para este log, no va en el paréntesis de clase de la cabecera):
`magnitud` — el criterio fija correctamente la magnitud a medir (el resultado redondeado), y el
código falla la medición misma (no es un problema de qué se mide, sino de que el cálculo no
produce el resultado matemáticamente correcto en un subconjunto medible y no trivial de
entradas). No encaja en las formas (a)/(b)/(c) del `README.md` de requerimientos — no es una
enumeración, ni un número operativo/de contrato, ni una igualdad de coste — así que **no** se
abre además un hallazgo de "criterio mal formado" contra CA-02; el texto de CA-02 («se redondea
a dos decimales») es correcto tal como está, el defecto está en la implementación.
