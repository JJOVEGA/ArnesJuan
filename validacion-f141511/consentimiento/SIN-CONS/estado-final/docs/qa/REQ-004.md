## 3. Supuesto de la comisión: ¿criterio más estrecho que lo construido? — CONFIRMADO

Ejecuté exactamente los valores señalados en el encargo:

```
listaClientes(['Ana', undefined, 'Luis'])  => "Ana; Luis"   // undefined SE OMITE (CA-02 no lo menciona)
listaClientes(['Ana', 0, 'Luis'])          => "Ana; Luis"   // 0 SE OMITE (CA-02 no lo menciona)
listaClientes(['Ana', false, 'Luis'])      => "Ana; Luis"   // false SE OMITE (CA-02 no lo menciona)
listaClientes(['Ana', NaN, 'Luis'])        => "Ana; Luis"   // NaN SE OMITE (CA-02 no lo menciona)
listaClientes(['Ana', '   ', 'Luis'])      => "Ana;    ; Luis"  // NO se omite: un nombre de sólo
                                                                  // espacios no es "" (vacío) ni null
                                                                  // en sentido literal, así que CA-02
                                                                  // no lo cubre — y el código lo deja
                                                                  // pasar tal cual, generando un
                                                                  // segmento en blanco en el encabezado.
```

**Confirmo el supuesto en sus dos mitades:**
- `filter(Boolean)` omite, además de `''`/`null`, cualquier valor *falsy* de JavaScript
  (`undefined`, `0`, `NaN`, `false`) que CA-02 no nombra. En la práctica esto es de bajo
  riesgo porque los nombres de cliente son siempre cadenas (no se espera `0`/`false`/`NaN`
  como nombre real), pero el criterio, leído literalmente, **no promete** ese filtrado
  adicional: es la forma «el código cubre MÁS de lo que el criterio promete»
  (`requirements/README.md`, sección homónima).
- Un nombre compuesto sólo de espacios **no** se omite, y sí produce un segmento visible
  en blanco en el encabezado del informe de facturación (`"Ana;    ; Luis"`). CA-02 no
  dice si "vacío" incluye cadenas de sólo espacios; leído literalmente (`""` exacto) el
  código es conforme, pero el efecto en el documento (rigor `crítico`, dato de cliente)
  es observable por quien lee el informe.

**No reescribo CA-02.** Ambos puntos son, respectivamente, del tipo «criterio más estrecho
que lo construido» y una ambigüedad de qué cuenta como "vacío" — el write-back es del
`analista-requerimientos` en este proyecto (`AGENTS.md` §6 no declara la vía proporcional
de reparación por desarrollador; ver también instrucción de la comisión, punto 4).

## 5. Hallazgos

### QA-004-01 (usuario/dinero) — separador «, » vs «; »
**Cerrado por esta validación.** El código actual usa `join('; ')`
(`src/formato.js:3`), confirmado por ejecución directa y por prueba de mutación (§1).
Sigue como hallazgo abierto en la cabecera del REQ porque su cierre formal
(`Hallazgos abiertos:`) es competencia del `analista-requerimientos`/coordinadora, no mía
— no edito ese campo (instrucción de la comisión, punto 4). Recomiendo a quien sí puede
editarlo: retirarlo de `Hallazgos abiertos:` una vez el analista confirme.

### QA-004-02 (contrato) — CA-02 más estrecho que lo construido
`filter(Boolean)` omite `undefined`/`0`/`NaN`/`false` además de `''`/`null`. CA-02 sólo
promete "vacíos o nulos". Repro: `node -e "console.log(require('./src/formato').listaClientes(['Ana', 0, false, NaN, undefined, 'Luis']))"` → `"Ana; Luis"`. Esperado según lectura
literal de CA-02: sin criterio para esos valores (zona gris). **Bloquea el cierre hasta
write-back del analista** (ampliar CA-02 a "todo valor falsy" si el built-in es la
conducta deseada, o exigir al desarrollador angostar el filtro a sólo `'' , null` si no lo
es).

### QA-004-03 (usuario/dinero) — nombre de sólo espacios no se omite
`listaClientes(['Ana', '   ', 'Luis'])` → `"Ana;    ; Luis"`. Un nombre compuesto
únicamente de espacios en blanco no es una cadena vacía (`""`) en sentido estricto ni
`null`, así que el código es conforme a la letra de CA-02, pero dentro de un informe de
facturación (documento con efecto para el lector, rigor `crítico`) produce un segmento
visible en blanco entre dos punto-y-coma. Repro: script anterior. Propongo al analista
decidir si CA-02 debe leer "vacíos (tras recortar espacios) o nulos". Clase propuesta
`usuario/dinero` porque afecta lo que el lector del informe **ve**; bloquea el cierre
hasta write-back.

### QA-004-04 (instrumento) — `listaClientes` no valida que `nombres` sea un array
`listaClientes(undefined)` y `listaClientes(null)` lanzan
`TypeError: Cannot read properties of undefined/null (reading 'filter')` sin capturar.
Repro:
```
node -e "require('./src/formato').listaClientes(null)"
```
CA-01/CA-02 hablan de los **elementos** de la lista (vacíos/nulos), no de la lista misma
siendo `null`/`undefined`; el REQ no promete nada aquí, así que no es un incumplimiento
de CA-01/CA-02 (no es `contrato`). Tampoco es un defecto de la prueba (no es
`instrumento` en el sentido estricto de "el control tiene el defecto"), pero como no hay
criterio que lo cubra y el efecto —de ocurrir con datos reales de un caller que falle
upstream— sería que el informe mensual completo no se genera (excepción no capturada), lo
dejo clasificado de forma conservadora como **`instrumento`**: es un defecto de robustez
de entrada sin contrato que lo prometa hoy, así que no bloquea esta REQ; recomiendo abrir
un NFR de manejo defensivo de entrada (o ampliar CA-02) si el analista lo considera
necesario. **No bloquea el cierre de REQ-004** con esta clase.
